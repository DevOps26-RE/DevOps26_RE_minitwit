## CI/CD pipelines, deployment, and release

Our CI/CD setup is implemented in GitHub Actions and is split across three workflows: `main.yml` (continuous integration + application deployment), `release.yml` (versioned releases), and `deploy-db.yml` (manual database infrastructure updates). The main pipeline runs on `push` and `pull_request` to `main`.

**Pipeline illustration**
`push/PR to main` → `static-analysis` → `test` → `build-and-push` → `deploy`
`push tag v*` → `create GitHub release`
`manual dispatch (stage/prod)` → `deploy DB compose`


Stage 1, **static-analysis**, enforces code quality using Go and multi-language tooling: `gofumpt` (formatting, with automatic commit/push of fixes), `golangci-lint`, `hadolint` for Dockerfiles, `htmlhint` for templates, and `yamllint` for YAML-based infrastructure/config files.  
Stage 2, **test**, starts an ephemeral Docker Compose test stack and executes integration/UI tests (web app, PostgreSQL, Selenium, and the test container), then tears the stack down with volume cleanup.

Stage 3, **build-and-push**, uses Docker Buildx, logs into Docker Hub, builds `docker/Dockerfile-app`, and pushes branch-aware tags. On `main`, images are tagged `prod-<shortsha>` and `latest`; on non-main contexts, they are tagged `test-<branch>-<shortsha>` and `test-latest`. For pull requests, the workflow also comments the generated image tag back to the PR for traceability.

Stage 4, **deploy**, copies `docker-stack.yml` and observability configs to the Swarm manager and executes `docker stack deploy` over SSH with environment-specific variables and secrets. The same deployment job targets staging or production by selecting hostnames, SSH keys, domain, and DB address from GitHub Variables/Secrets based on the Git ref.

For **release management**, pushing a semantic tag (`v*`) triggers `release.yml`, which creates a GitHub Release with autogenerated notes. Database updates are intentionally separated: `deploy-db.yml` is manually triggered with an explicit `stage`/`prod` choice and applies `docker-compose-db.yaml` on the DB droplet, acknowledging short downtime during updates.

In addition to commit-driven CI/CD, we use a **one-click environment deployment** flow for infrastructure bootstrap in staging. Running `terraform apply` in `terraform/stage` provisions the DigitalOcean VPC, droplets, and firewall rules, generates `ansible/inventory_stage.ini` plus `.env.stage`, and then triggers Ansible automatically (`null_resource` + `local-exec`) to configure the hosts and bring up the stack. This gives us a push-button path from “no servers” to a runnable platform. Once the environment exists, regular GitHub Actions deployments take over for iterative application releases.
